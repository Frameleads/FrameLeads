# Prospect memory (roadmap item 3)

Apply `20260928120000_prospect_memory` through the normal, explicitly selected deployment database workflow before enabling code that reads memory. The migration only creates `ProspectMemoryState` and `ProspectMemoryEvent` plus tenant-scoped keys and indexes. It was not applied during implementation.

`recordProspectMemoryEventInTransaction` is the shared writer. A source tuple `(userId, prospectId, sourceType, sourceId, eventType)` is unique; repeat deliveries insert no second event. Call it in the transaction that commits a canonical action. `recordProspectMemoryEvent` is the standalone wrapper. Events contain short descriptions, source identity, importance and timestamps. They are append-only in application code. The state holds only a bounded rolling summary and event count; qualification, research and identity remain canonical in their existing tables.

The Scout detail read lazily seeds a Prospect baseline and up to 20 existing leads, 20 inbound signals and 20 successful outbound logs. This is a bounded best-effort historical snapshot, not a full backfill. Repeated reads deduplicate by canonical source IDs. There is no AI or external network use. `getProspectMemoryContext` returns at most 20 purpose-selected events, a 1,200-character rolling summary and a 3,000-character event text. Callers must provide the authenticated user's ID; tenant ownership is verified before initialization.

Current producers are lead linking, inbound signal creation, changed qualification, human qualification override, newly committed READY research, Sandbox handoff and confirmed outbound send logs. A READY research cache hit produces no event. A repeated Sandbox handoff to the same lead produces no second event. A send-log memory write failure is logged after successful dispatch; the lazy initializer can replay the canonical log. No model calls, prompt changes, new providers, queue or production backfill are part of this feature.
