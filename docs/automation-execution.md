# Governed execution V1

Roadmap #8 adds deterministic autonomy resolution to a completed Inbox Decision. It does not change Decision classification or its immutable DecisionTrace. The three modes are `AUTOPILOT`, `HUMAN_APPROVAL`, and `MANDATORY_ESCALATION`. Execution states such as `BLOCKED`, `HELD`, `EXECUTING`, `EXECUTED`, `REJECTED`, and `FAILED_UNCERTAIN` describe what happened to an action, not new modes.

## Controls and precedence

`AutomationPolicy` is one tenant-owned policy. If no row exists, reads return safe defaults: human approval, Autopilot disabled, tenant auto-execution disabled, confidence threshold 90, daily automatic-send cap 20, and human-approval fallback. The server flag `AUTOMATION_EXECUTION_ENABLED` must separately equal `true` before any automatic send. Its default is disabled. `DECISION_ENGINE_ROLLOUT_MODE` independently controls automatic *analysis* and still defaults to `MANUAL`.

FrameLeads currently has tenant-owned `LeadList` records, not a canonical Campaign model. `AutomationCampaignOverride` therefore attaches to an owned lead list through a composite tenant foreign key. `INHERIT`, the three modes, and `DISABLE_AUTOMATION` are supported. This is a source-group override and does not claim that an external sender campaign has the same identity. `ProspectHold` is a separate tenant-owned operational stop; release is explicit. Confirmed provider unsubscribe signals remain the authoritative suppression input.

The resolver re-reads tenant ownership, current policy and list override, confirmed unsubscribe, Prospect hold, current Constitution, Decision review/confidence/draft, Brain/Playbook revisions, sender availability, previous actions/attempts, and the automatic-send cap. In order of authority: an already claimed execution is terminal; confirmed unsubscribe or Constitution `BLOCK` blocks; Prospect hold holds; Constitution `REQUIRE_HUMAN`, `REQUIRE_SAFE_RESPONSE`, unresolved rules, unconfigured Constitution, or unconfirmed unsubscribe intent escalate; Constitution `REQUIRE_APPROVAL` forces human approval; a requested mandatory or human mode remains restrictive. Autopilot then requires explicit tenant enablement, both execution switches, a READY Decision with no review reason, threshold confidence, safe draft, connected native sender, current context, and capacity under the cap. Otherwise it falls back to human approval or mandatory escalation. Resolution makes zero model calls.

Current Constitution is evaluated for outreach, topic response, and the actual proposed claim on every resolution and again immediately before an execution claim. The edited text, not merely the original draft, is checked. This can block an old Decision after a policy change. The append-only `DecisionAutomationResolution` rows capture mode, state, reasons, rule IDs, policy revision, decision-time and execution-time Constitution revisions. Changed Brain/Playbook context prevents Autopilot and signals re-analysis; it never silently spends another model call.

## Actions and routing

The authenticated Inbox action bridge derives the tenant from the existing session. `APPROVE` sends the current suggested reply; `EDIT_AND_SEND` stores both original and edited text; `REJECT` stores a bounded reason without sending; `ESCALATE` stores a reason and creates or reuses the tenant-owned `DecisionAssignment` in a bounded internal queue. There is no team-member assignment claim or SLA timer. The Inbox also supports a Prospect hold and links to compact Automation settings. Legacy Smartlead triage approval refuses signals with a Decision, directing them to the governed path. The generic manual email route remains a separate existing workflow; it is not an alternative Decision approval endpoint.

Sending reuses the existing native SMTP implementation through a shared server helper. A unique tenant/Decision execution attempt and deterministic idempotency key are claimed transactionally before SMTP. An attempt is single-use: HTTP retries, double clicks, and scheduler retries cannot initiate a second SMTP call. SMTP has no reliable provider idempotency guarantee, so provider or commit uncertainty is recorded as `FAILED_UNCERTAIN` and never retried automatically. Successful sends persist the existing `OutboundLog`, a canonical outbound `ConversationMessage`, and a `DecisionExecutionAttempt` with content fingerprint, bounded sent content, provider message ID, actor/mode, and Constitution revisions. Human actions are append-only `DecisionActionEvent` rows with unique request keys. Meaningful human and successful send events enter Prospect Memory idempotently; reads and validation failures do not create Memory events.

No AI provider, extra draft, fake token usage, Revenue-at-Risk score, SLA engine, Sandbox, Replay UI, or Outcome Learning is part of this implementation. The audit records are designed to support later Replay without rewriting DecisionTrace.

## Rollout

Apply the additive `20260928170000_governed_automation_v1` migration only through a reviewed deployment to the intended database. Deploying the migration alone cannot enable automatic sending. Keep `AUTOMATION_EXECUTION_ENABLED` unset or `false` until separately approved, and require a tenant to explicitly set `autopilotEnabled`, select Autopilot, and release the tenant kill switch. Verify native mailbox connection and Constitution configuration first. Production migration, backfill, real send, and AI provider calls are outside this coding task.
