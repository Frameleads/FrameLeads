# Inbox Decision Engine V1

Roadmap #7 adds tenant-owned `Conversation`, `ConversationMessage`, `Decision`, and `DecisionTrace` without replacing `InboundSignal`, `OutboundLog`, or existing Inbox workflows. The migration is additive and is **not** applied by this change. Apply it through the normal reviewed deployment process before using the new Inbox packet in an environment.

Inbound replies are persisted first. The shared inbound persistence helper projects each tenant-owned reply into a source-keyed conversation message in the same transaction when a Prospect is linked. Existing records are lazily projected, at most 30 inbound and 20 outbound source records per Prospect. `OutboundLog` does not store actual sent text, so the projected outbound message has a null body. Unlinked replies remain stored and require manual identity review; no cross-tenant lookup is attempted. Source uniqueness on `(userId, sourceType, sourceId)` prevents duplicate conversation messages. Provider message IDs are retained where available. The legacy `/api/replies/ingest` cold path now persists an archived inbound record instead of discarding it.

The authenticated `POST /api/decisions/triage` accepts `signalId` and optional `retryOfDecisionId`; it derives user identity from the session. `DECISION_ENGINE_ROLLOUT_MODE` is a server-only control: absent, `MANUAL`, or unrecognized values default to **MANUAL**, which allows Inbox Analyze/Re-analyze but schedules no automatic Decision Engine work. `DISABLED` blocks both automatic scheduling and the manual API. Only explicit `SHADOW_AUTO` schedules best-effort idempotent triage with Next.js `after()` after the canonical inbound transaction commits. The scheduler runs at most two workers concurrently; provider failure or interrupted after-response work cannot reject the inbound response. The Inbox packet can trigger or retry the same idempotent service on demand when enabled. No Decision action sends, routes, archives, or approves a message. The authenticated `GET /api/decisions?signalId=` returns the latest packet and trace for one tenant-owned reply. The route never accepts a client-provided user ID. Existing legacy classifiers remain active and unchanged; automatic duplicate Decision Engine spend requires an explicit `SHADOW_AUTO` opt-in.

For a nuanced reply, one Gemini 2.5 Flash call returns a strict JSON candidate with one primary and up to four secondary intents, evidence spans copied from the current reply, confidence, interpretation, a candidate action, explanation, and optional draft. The prompt treats reply content, history, imported notes, and website material as untrusted data; the model has no tools or action authority. Server validation rejects unknown taxonomy values, unexpected keys, invalid scores, unsupported evidence spans, and malformed fields. There is no repair loop or weaker fallback model. Provider failure or malformed output yields a review packet with unresolved intent. Deterministic bypasses require a trusted server-originated `SYSTEM_AUTO_REPLY` or `UNSUBSCRIBE_CONFIRMED` marker; no free-text keyword drives those fast paths.

The context composer includes the current reply, eight recent messages, six memory events, six Brain entries, four Playbook rules, five Constitution rules, canonical ICP qualification and fit, and stored account facts. It caps the current reply at 4,000 characters, conversation at 2,800, Memory at 1,300, Brain at 1,700, Playbook at 1,300, Constitution at 1,400, and total request context at 12,000. It records memory event IDs, context references, and Brain/Playbook/Constitution revision numbers in a SHA-256 context fingerprint and DecisionTrace. No prospect memory or ICP score is re-inferred by the model.

After the candidate output, the deterministic Sales Constitution evaluator checks relevant topics, proposed draft claims, and outreach. A block results in `NO_SALES_OUTREACH`; any constrained or unresolved policy requires review and suppresses the model draft. Matched, blocked, unresolved, and winning rule details are retained in the trace. Playbook text cannot override this evaluation. Decisions start as `PENDING` and finish as `READY` or `NEEDS_REVIEW`; low confidence, contradictions, missing Constitution configuration, provider errors, and unresolved rules require review. The decision row and trace are finalized together. Completed rows are not rewritten; explicit re-analysis creates a version linked by `supersedesDecisionId`. A unique tenant/message/type/fingerprint key claims a decision before model invocation, so duplicate requests reuse the pending or completed packet without a second call.

`AIUsageEvent` is written only after a provider request actually starts. Cached decisions and deterministic markers record no model usage. The ledger stores provider/model, feature/operation, usage tokens if returned, latency, and success/failure. A ledger write failure is logged and forces review rather than leaving a pending decision. No real provider call is made by local tests.

The shared Decision shape leaves `automationMode`, `assignedOwnerId`, `revenueAtRiskScore`, and `slaDueAt` null. These are owned by later roadmap items. The new packet is explicitly in shadow mode: it does not change existing inbox dispatch, approval, or routing behavior. Legacy classifiers remain separate; the on-demand V1 packet does not invoke them.

Safe local validation: `npx prisma format`, `npx prisma validate`, `npx prisma generate`, `npx tsc --noEmit --incremental false`, `npm run test:decision`, relevant regression tests, and `git diff --check`. Do not run `npm run build` against an unknown database because it executes `prisma migrate deploy`.
